# ctx: a token-efficient repo index for Claude Code

ctx builds a compact, committed map of a repository that AI agents read **instead of** the source:
a code tree, a git-history tree and the DB schema, plus an optional LLM layer with one-line file purposes,
module summaries and history digests.

The main use case: a client sends a change request, and you need real tickets plus the questions to ask
back, without having an agent read the whole codebase. The same index also helps Claude Code write code,
because it shows callers (`u:`) and files that historically change together (`cc:`) before an edit.

**Measured** on [umami](https://github.com/umami-software/umami) (1,652 files):

| | Tokens |
|---|---|
| Raw source | ~1.8M |
| Root summary, loaded at every session start | ~1.7k |
| Slice for one change request (`q`) | ~3k |
| Ticket scoping in one call from the slice (no tools) | 16k context, $0.13 |
| Same in plain Claude Code, no index | 210k context, $0.17 |

---

## Files

| File | Goes where | Purpose |
|---|---|---|
| `ctx.py` | anywhere (init copies it to `.ctx/ctx.py`) | the whole tool, one file, Python 3.10+ |
| `SPEC.md` | next to `ctx.py` (init copies it) | the CTX1 format, for humans and agents |
| `.github/workflows/ctx-check.yml` | your repo, optional | CI check that the committed index is fresh |
| `service/`, `Dockerfile` | a server, optional | HTTP API over the index (see Service) |
| `README.md` | this file | |

Everything else (Claude Code hooks, skills, `CLAUDE.md` block, git hook) is generated by `init`.

## Requirements

- git, Python 3.10+
- `pip install tree-sitter-language-pack` (add `--break-system-packages` on system Python)
- For the LLM layer only: the `claude` CLI logged in (uses your subscription), **or** `ANTHROPIC_API_KEY`

Parsers: TypeScript/JavaScript (incl. TSX, ESM/CJS) and Python. Other files are indexed for path, history and facts.

## Quick start

```bash
cd your-repo
python3 /path/to/ctx.py init --sync      # index + Claude Code integration + LLM layer
git add .ctx .claude CLAUDE.md
git commit -m "add ctx repo index"
```

Without `--sync`, run the LLM layer later with `/ctx-sync` in Claude Code, or `python3 .ctx/ctx.py sync run`.

Then in Claude Code:

```
/ticket The client wants a PDF invoice emailed to the team owner after each Stripe payment
```

## What `init` installs

| Path | What |
|---|---|
| `.ctx/` | the index plus `ctx.py` and `SPEC.md` |
| `.claude/settings.json` | `SessionStart` hook (refreshes the index and injects the root summary), plus permissions for `ctx.py` |
| `.claude/skills/ticket/` | `/ticket`: change request → gap check → client questions with defaults → tickets |
| `.claude/skills/ctx-sync/` | `/ctx-sync`: fill or refresh the LLM layer |
| `CLAUDE.md` | a short block (between `<!-- ctx:start -->` and `<!-- ctx:end -->`) telling Claude how to use the index |
| `.git/hooks/pre-commit` | rebuilds the index and stages it with each commit |

Re-running `init` is safe: it updates the tool, the skills and the `CLAUDE.md` block in place and merges settings.
It warns if your `.gitignore` excludes `CLAUDE.md` or `.claude/`, because teammates wouldn't get them.

Options:
- `--strict` adds a `PreToolUse` gate. The first grep/glob of a session is blocked once with "run `ctx.py q` first". It never blocks twice.
- `--sync` runs the LLM layer right after init.

## Commands

```bash
python3 .ctx/ctx.py q "add email alerts when daily visitors drop"   # context slice for a task
python3 .ctx/ctx.py show f59d8ef m51a97                             # expand file / module ids
python3 .ctx/ctx.py db user website                                 # schema: columns, pk*, fk→, writers
python3 .ctx/ctx.py setp lib/billing.ts "Invoice totals and tax"    # human purpose (wins over generated)
python3 .ctx/ctx.py build                                           # rebuild (incremental, ~0.2s)
python3 .ctx/ctx.py check                                           # CI: exit 1 if committed index is stale
python3 .ctx/ctx.py sync status|plan|apply|run                      # LLM layer
```

Read commands (`q`, `show`, `db`, `todo`) refresh the index first, so it's never stale mid-session.

## What's in the index

```
.ctx/
  root.ct        repo header + one entry per module: purpose, key exports, deps, facts      (always loaded)
  n/<mod>.ct     c-tree: per file: exports (x), imports (i), used-by (u), facts (e)
  db.ct          schema: table(col* = pk, col→table = fk) <defined-in w:<writer files>
  idx.tsv        search terms → file ids
  purposes.tsv   file purposes        ┐
  mods.tsv       module purposes      │ LLM layer, committed
  hist.ct        history digests      │
  OVERVIEW.md    human overview       ┘
  g/             g-tree: per-file history, co-change, ticket refs          (local, rebuilt from .git)
```

Example file block:

```
@f160fd5 app/api/stripe/webhook/route.ts L=34 h=970d9ec3
p: Stripe webhook: verifies signature, handles subscription events, syncs teams table status
x: POST(request: NextRequest)
i: fa169f8 | ext:next,stripe
e: env:STRIPE_WEBHOOK_SECRET route:POST /api/stripe/webhook
```

Facts (`e:`): `env:` variables, `db+:` tables defined, `db:` read, `dbw:` written, `route:` HTTP routes.
Schema sources: Drizzle, Prisma, SQL migrations (CREATE/ALTER replayed in order), SQLAlchemy, SQLModel, Django.
Usage sources: Drizzle, Prisma-style calls, Supabase `.from()`, Django, SQLAlchemy, raw SQL in strings.

Full format: [SPEC.md](SPEC.md).

## LLM layer (`sync`)

The builder never calls a model. `sync` adds meaning in three incremental phases:

1. **files**: a one-line purpose per source file, redone only when the file's content hash changes
2. **mods**: a module purpose (redone when the module's structure changes) and a history digest of up to 8 milestones from commits (updated after 3+ new commits)
3. **overview**: `OVERVIEW.md`, covering architecture, data model, evolution, hotspots and gaps to verify

Measured with Haiku:

| Repo | Files | Full sync | Incremental |
|---|---|---|---|
| saas-starter | 51 | $0.13, ~1 min | $0.03 |
| umami | 1,652 | ~$2.30, ~2.5 min (`-j 8`) | cents |

How to run it:
- `/ctx-sync` in Claude Code. It runs the headless sync and falls back to Haiku subagents (about 2–3x more expensive).
- `sync run [-j 8] [--max N] [--api]` headless, for CI or a service.
- Or any runner you like: `sync plan` writes self-contained prompts to `.ctx/.sync/`, your runner writes `*.out`, then `sync apply` validates and merges.

`apply` rejects output for files that changed in the meantime. Purposes you write with `setp` are never overwritten for the same content.

## Keeping it fresh

| When | What |
|---|---|
| Every read command and session start | incremental refresh (~0.1–0.2s) |
| Every commit | pre-commit rebuilds and stages `.ctx` |
| CI | `ctx.py check` (see `.github/workflows/ctx-check.yml`) |
| Occasionally | `/ctx-sync` (the session start prints a hint when the LLM layer is behind) |

The root summary only changes when structure changes (modules, exports, deps, facts), never on a body edit or a
commit. That keeps it usable as a cached prompt prefix.

## Claude Code in the browser (claude.ai/code)

Cloud sessions use the committed `CLAUDE.md`, skills and hooks (single-repo sessions). On a cloud VM the session hook
installs `tree-sitter-language-pack` and deepens a shallow clone so history is available.

Multi-repo sessions (projects) don't run repo hooks. Add `pip install tree-sitter-language-pack` to the environment's
setup script there.

## Service (HTTP API)

`service/` serves the index of GitHub repos over HTTP, for apps that let a model scope tickets
without a checkout of their own. FastAPI, one container (`Dockerfile`, `compose.example.yaml`).
It never calls an LLM: the caller does, and uses these routes as the model's tools.

- Keeps a blobless bare clone per repo (full history, file contents on demand) and one worktree
  per branch (least recently used ones removed past `CTX_MAX_WORKTREES`). Fetches at most every
  `CTX_FETCH_EVERY` seconds, or now with `refresh: true` / `POST …/refresh` (e.g. on a push webhook).
- Uses the committed `.ctx/` of the branch (purposes, module summaries stay) and rebuilds only what
  is missing: the git history part and files changed since. Repos without `.ctx/` get the structure
  index without the LLM layer.
- Auth: `Authorization: Bearer $CTX_API_KEY`. The git token comes per request in `X-Git-Token`
  (e.g. a GitHub App installation token); it lives only in the environment of that request's git
  commands, never on disk, in git config or in logs. Run it on an internal network.

| Route | Body | |
|---|---|---|
| `GET /health` | | `{ok, version}` |
| `POST /repos/{owner}/{name}/root` | `{ref?}` | root summary |
| `POST /repos/{owner}/{name}/q` | `{ref?, text, budget=3000}` | slice for a task |
| `POST /repos/{owner}/{name}/show` | `{ref?, ids[]}` | file / module blocks |
| `POST /repos/{owner}/{name}/db` | `{ref?, tables[]}` | schema lines |
| `POST /repos/{owner}/{name}/refresh` | `{ref?}` | fetch + build now |
| `DELETE /repos/{owner}/{name}` | | drop the cached clone |

`ref` = branch, default the repo's default branch. Answers: `{text, ref, head, indexed, stale, tokens, ms}`
(`stale`: the committed index is behind the branch, so changed files have no purpose yet).
Errors: `{error, code}` with 401 (service key), 403 (the token can't read the repo), 404 (branch),
409 (repo busy), 422 (bad input), 502/504 (git).

```bash
docker build -t ctx-service .
docker run -e CTX_API_KEY=… -v ctx-data:/data -p 127.0.0.1:8080:8080 ctx-service
curl -s localhost:8080/repos/acme/shop/q -H "Authorization: Bearer …" -H "X-Git-Token: $TOKEN" \
     -H 'content-type: application/json' -d '{"text": "refund an invoice"}'
```

Env: `CTX_API_KEY` (required), `CTX_DATA` (`/data`), `CTX_GIT_BASE` (`https://github.com`),
`CTX_MAX_WORKTREES` (20), `CTX_FETCH_EVERY` (30). Tests: `pip install -r service/requirements.txt pytest httpx && pytest service/tests`.

## Limits

- Imports resolve through the nearest `tsconfig`/`jsconfig` (`paths`, `baseUrl`, relative `extends`) and workspace packages (any `package.json` in the repo, by `name` and `exports`/`main`; built `dist/` entries fall back to `src/`). Package `extends` (e.g. `@tsconfig/node20`) and TS project references are not followed.
- No Go, Rust, PHP or Java parsers yet. Those files get path, history and facts, but no exports or imports.
- Search (`q`) is lexical. Files without a purpose can be missed on purely semantic requests, which is what `sync` fixes.
- The `--api` runner is implemented but untested. All measurements used the `claude` CLI.
- Org-managed "managed hooks only" settings disable repo hooks. An admin would need to add them as managed settings.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `ModuleNotFoundError: tree_sitter_language_pack` | `pip install tree-sitter-language-pack` |
| `check` fails in CI | `python3 .ctx/ctx.py build && git add .ctx`, or install the pre-commit hook via `init` |
| Permissions from `.claude/settings.json` ignored | Trust the workspace once in interactive Claude Code |
| `sync run` says it needs the claude CLI | `claude` login, or `export ANTHROPIC_API_KEY=… && ctx.py sync run --api` |
| Sync line rejected | normal when a file changed during sync. It's retried next round |
